最核心的抽象，其实就是 workflow 这个抽象。因为 workflow 把工作流程积累了下来，我可以写很多很多的工作流程，不断地去整合它们。这样一旦工作流程显性化，很多操作就好做了。

这个简直是太重要了！他终于解决了我最大的麻烦，就是怎么把这种工作习惯传递出去。现在终于可以传递出来了。

虽然它还有很多限制，比如说受到我们对于产物的定义的限制、各种操作工作工具的限制，但是已经足够用了。

我的助理拿着 AI 试了一下，说大部分流程能猜得出来，少数不行。那就证明这个程序还是非常重要的，这是意料之中的情况。

这个工作方法肯定有它的边界，但是，比如它套一个 PI 然后去把各种工作流程串起来，绝对是非常有用的。它可以很大程度上起到把流程注入进来的感觉，并且比 skill 要靠谱。

在想它可以跟 PI 的工具链对起来，或者跟其他各种各样的 Agent 工具对起来，以工具为单位去编排。

因为我们现在做的主要操作其实就是 read file, edit file，然后 run bash。对，就这个足够编排了。哪怕是其他一些工具，再复杂一点，无非就是增加一些 web search 之类的工具，我们完全可以编排。

核心的点就在于，我们每个步骤后面都放一个验证的方式，这样流程会更稳定一点。

而且最主要的是，错了之后，我们可以直接去编辑这个流程，这个流程也可以直接保存下来复用。这样的话，就比 skill 要靠谱很多。

尽可能跟大部分智能体使用同一套语言，其实对我们做事比较有帮助，这样可以很好地复用这种基础设施。至于 PI，我觉得它足够简单，所以可以从它开始。

用显式、可验证、可编辑、可复用的 workflow，把 Agent 的工作习惯沉淀成基础设施；从简单 PI 工具链开始，与通用 Agent 工具语言对齐，是最务实的路径。

如果只留四条，我认为是：

1. 流程可显式化；
2. 工具可安全、幂等执行；
3. 每步结果可自动且可信地验证；
4. 失败可恢复、可审计、可追责。

这四条成立，这个范式可以上“受控生产”。
缺一条，它更适合做 copilot / 辅助自动化，而不是无人值守生产。

一句话总结：
这个范式能上生产，前提是把它当“代码 + CI + 权限系统 + 审计系统”来建设，而不是当一套 prompt 集合。最核心的假设是：每步验证比每步生成更可靠。如果验证器不可信，整个范式就不成立。

对，这个我们的基本假设是呃人机交互为主，然后呢，当人机交互到了一个人脱手的阶段，然后再把它放在那里，然后嗯或者是把它分装成专门的工具。

你可以把它看成一个成熟度演进：

1. 人主导，AI 辅助：人做决策，AI 给建议。
2. AI 提议，人确认：workflow 开始显性化。
3. AI 执行，人审核：每步有验证，人看结果。
4. AI 执行，人监控例外：人从 in-the-loop 变成 on-the-loop。
5. 人脱手：正常情况不介入，异常才接管。
6. 分装成专门工具：把稳定 workflow 固化成窄接口、确定性代码或专用 Agent 工具。

所以“脱手”不是人消失了，而是人的判断被沉淀到了几个地方：

· 每步的验证器；
· 异常检测和回滚；
· 审批和权限边界；
· 审计和可观测性；
· 人工接管入口。

判断一个 workflow 能不能脱手，我觉得可以看这几个信号：

· 成功率稳定，方差小；
· 人工干预率持续下降；
· 异常能被自动发现，而不是靠人偶然看到；
· 验证器能覆盖主要失败模式；
· 输入输出边界清晰；
· 出错能回滚、能重放、能接管；
· 流程变更时有人能直接编辑和回归测试。

而“分装成专门工具”是更进一步：把 workflow 里最稳定、最重复、最不需要推理的部分压缩成工具。这样它就不再每次靠模型猜，而是变成可靠的基础设施。工具内部可以是确定性代码，也可以是更窄的 AI，但对外接口要稳定。

这个路径最大的好处是：不需要等所有前提都成立才上生产。只要人还在环上兜底，workflow 可验证、可回滚、可接管，就能先上受控生产。等某个分支跑稳了，再把它脱手、分装、固化。

风险也有两个：

· 过早固化：流程还没稳定就做成工具，后面改起来很僵；
· 验证器腐化：流程变了，验证没变，脱手后错误会被放大。

所以关键还是那句话：
人机交互为主时，workflow 是积累和交接的载体；人脱手时，验证器和异常接管是安全绳；分装成工具时，契约、权限、审计和版本化是生产门槛。
