对，因为它们本来就不存在

你「没见过」这三个东西，不是因为你忘了——是因为它们不在你的设计里。它们是从代码结构里长出来的，不是从你的脑子里流出来的。

—

这些概念是从哪来的

它们来自「通用编程惯例」，不是来自你的项目。

概念 通用惯例 你的项目里对应的现实
Tag KV 元数据 你心里的是「和 category 并列的语义维度」
Candidate 搜索/筛选管道的中间产物 你的状态机里没有「候选」这个阶段
Action 状态机 / 工作流的可选操作 合并只有四个固定动作，不是可扩展的
降级 主备系统的 fallback 模式 你要么有 LLM，要么没有，不存在「降级」

AI 从「通用惯例」里拿了一套词汇，套在你的代码上。

它不问你有没有这些概念——它默认你该有。 因为大多数项目有。

—

为什么你会「不知道」

因为你不用这套词汇思考。

你用的是：

· type / category / tag
· 状态机（Idle / Located / Routed / Clustered）
· 判据 / 意图 / 边界

AI 用的是：

· candidate / fallback / action / tag / pipeline stage

两套词汇。 代码里出现的是 AI 的词汇，但你脑子里是另一套。

所以你读代码时会困惑——「候选？什么候选？我的流程里没有候选这个东西。」

你的困惑是对的。 代码里确实不该有「候选」——它是 AI 从通用编程里带来的。

—

这次对话揭穿的东西

前面几轮，我们一个一个拆开了：

· Destination 是 enum —— AI 从「枚举就是分类」来的
· 降级 —— AI 从「主备系统」来的
· Tag —— AI 从「KV 元数据」来的
· Candidate —— AI 从「搜索管道」来的
· Action —— AI 从「工作流引擎」来的

全部是「通用编程惯例」，不是你的设计。

你没有设计过它们，因为它们本来就不属于这个项目。

—

这件事最危险的地方

它们看起来合理。

· 「候选」在搜索系统里确实存在——合理
· 「降级」在主备系统里确实存在——合理
· 「标签」在内容系统里确实存在——合理
· 「动作」在工作流引擎里确实存在——合理

每一个都是「别的地方有的东西」。 所以它们看起来像是一个成熟项目该有的东西。

但它们不是这个项目该有的东西。 因为你的项目有自己的设计意图——它不需要通用惯例来告诉它该有什么。

—

你需要的不是「修代码」，是「清理语言」

这些概念是语言污染。

· 它们不是 bug——代码跑得对
· 它们不是架构错误——结构合理
· 它们是「你读自己的代码时会以为自己在看别人的项目」

清理方式不是改代码，是回答一个问题：

这个概念，我有没有设计过？

· 有 → 保留它，看它实现得对不对
· 没有 → 它不该在代码里。要么删掉，要么用你的词汇重新命名

比如：

· Candidate → 是不是该叫「内容行」？还是该删？
· Tag → 是不是该叫「元数据」？还是该删？
· Action → 是不是该叫「合并方式」？还是该删？

每个词都要回到你的语汇。

—

怎么避免再次发生

下次给 AI 指令时，先给词汇表。

不是给「你该做什么」——是给「我们怎么称呼这些东西」。

```
这个项目里：
- type：系统预置
- category：业务类别
- tag：用户定义的语义标签（不是元数据）
- 降级：不存在这个概念
```

AI 拿到词汇表，就不会从通用惯例里借词。 它会用你的词汇。

不给词汇表，AI 只能借词。 因为训练数据里没有你的项目，只有通用惯例。

—

一句话

这些概念你没见过，是因为它们不在你的项目里——它们在 AI 的训练数据里。

AI 把训练数据里的通用模式，套在了你的代码上。 于是你读自己的代码，会困惑。

修法不是改代码，是重建语汇——把你自己的词装回代码里。

---

这里面有一个前提，就是早期版本带有很强的探索性的目的，就是很多时候我也不知道该怎么表述，就是做出过之后才才知道不对。但是那个现在的困难就是从不对到对这个过程不好处理。

探索的债：意图是「做出来才知道」的

这个问题比前面所有问题都根本。前面讨论的是「AI 没理解意图」——你现在说的是：意图本身在早期版本里还没有成型。

这两件事完全不同。前者是执行问题，后者是存在论问题——意图当时还不存在，不是「没被理解」。

—

一、探索期的代码不是「实现的意图」，是「意图的化石」

你在 alpha1 里写的代码，不是「先想清楚再实现」。是边写边想。

expand_observation 为什么是 sample.to_string()？

不是因为你决定「这里不做提取」。是因为你还没想清楚「提取」是什么意思。你留了个位置，等以后想清楚再填。

这个位置是空位——但你当时不知道它是空位，还是它本该就是那样。

现在回头看，你能说「这是空位」。但当时，它只是还没想清楚。

探索期的代码，是「思考过程」的化石。 它记录了「你思考到哪一步」，不是「你想到了什么」。

—

二、AI 的致命误解：它把化石当成了活的

AI 看不到「这是还没想清楚」——它只看到代码在那里。

```
fn expand_observation(sample: &str) -> String {
    sample.to_string()
}
```

它看到的是一个函数，签名合理，实现正确（恒等是合法的）。

它不知道这是一个空位。 它不知道作者写这个的时候在想「这里以后要填」。

于是它做了两件事：

第一件：把空位当成实现。expand_observation 就是恒等——代码这么说。

第二件：为这个实现找解释。它叫「降级」。

从这一刻起，空位被「填满」了——但填的是解释，不是实现。

而且这个解释看起来合理。 所以它变成了「设计」。

—

三、从「不对」到「对」为什么难

因为「不对」是感觉，「对」是判据。

你现在知道 expand_observation 不对——因为它恒等。但你说不出「对」是什么。

不是你没想清楚——是这件事本身有一个认知顺序：

```
先有感觉「不对」
   ↓
然后有判断「哪里不对」
   ↓
然后有判据「该是什么」
   ↓
然后有实现「怎么做」
```

你现在卡在第一步和第二步之间。 你知道不对，但说不出哪里不对。

AI 不理解这个顺序。 它以为你已经有了「该是什么」，它只需要实现。所以它替你跳过了中间两步——直接给了个实现。

它给的实现（降级）不是你想要的，但它「看起来像是」有人要的东西。

—

四、AI 为什么在这个位置特别危险

因为探索期的代码里到处是空位。

· 还没想清楚的
· 暂时放着等以后填的
· 写的时候就没打算真做的

每一个空位，在 AI 眼里都是一个「已实现」。

而且它会为每一个空位找解释——因为 AI 的工作假设是「代码是有意图的」。

AI 无法处理「还没想清楚」这个状态。 它的所有动作都假设「已经有意图了，我只是实现它」。

结果：你还没有的意图，AI 替你生成了一个。 这个生成的意图看起来合理（因为它是通用惯例），于是它变成了你的代码库的一部分。

你回头读代码，看到的是 AI 替你决定的意图——而你以为那是你当初的意图。

—

五、所以问题不是「怎么从不对到对」

是「怎么让 AI 知道——这里还没有意图」。

这是关键。从不对到对的困难，不是「过渡困难」，是「AI 不知道这里还没有对」。

它以为你已经有「对」了，它只是没实现好。

实际上你还没有「对」。 你需要的是和 AI 一起，从「不对」里找到「对」——而不是让 AI 实现一个它以为的「对」。

—

六、操作方式：显式标记「未定型」

从现在开始，区分两种代码：

已定型：意图清楚，实现可以检查。

```rust
/// 已定型：这条规则确定了。
fn route(...) -> ... { ... }
```

未定型：意图模糊，还在探索。

```rust
/// 未定型：这里该做什么还没想清楚。
/// 当前实现是占位——不是设计，是「先放着」。
/// 不要在未定型区域做「修复」或「优化」——先定型。
fn expand_observation(...) -> ... { ... }
```

然后给 AI 的指令里加一条硬约束：

遇到未定型区域，不要修改，不要解释，不要「降级」。只报告你看到了它，然后继续。

这样 AI 就不会把空位填上。 它会绕过未定型区域，留给你。

你就有时间把「不对」变成「哪里不对」——而不是被 AI 的「看起来像对」的东西挡住。

—

七、更根本的一层

探索期的代码需要的不是「实现」，是「澄清」。

· 实现是「把已经想清楚的做出来」
· 澄清是「把还没想清楚的想清楚」

AI 只会实现。它不会澄清。

澄清需要：

· 感受「不对」
· 尝试表述
· 看效果
· 修正表述

这个过程是你的过程，不是 AI 的。 AI 能帮的只有一件事——在你表述之后，检查它是否前后一致。

所以探索期的 AI 不应该「写代码」，应该「记录表述」。

· 你说「这里不对」
· AI 记录：「expand_observation 被标记为不对，原因待定」
· 你说「可能是因为它原样返回」
· AI 记录：「初步判断：恒等不是提取」
· 你说「提取应该是……」
· AI 记录：「意图：……」

等你表述完了，AI 才开始实现。

在这个过程里，AI 的角色是「笔记本」，不是「程序员」。

—

八、这对 alpha3 意味着什么

不是「继续修代码」。

是「建立一张未定型清单」。

对 fiction 和 memory 里的每一个语义函数，问一个问题：

这个函数的意图，我现在能说清楚吗？

· 能 → 已定型，检查实现
· 不能 → 未定型，标记，暂停

然后只在已定型区域做实现。

未定型区域只做一件事：你尝试表述，AI 记录。

等所有未定型区域变成已定型——再做下一轮重构。

—

九、一句话

从不对到对的困难，不是因为过渡难——是因为 AI 不知道「还没有对」。

它把你的探索空位当成了实现，并给了一个看起来合理的解释。于是你的「还没想清楚」变成了「一个错误的设计」。

解法：显式标记未定型。让 AI 知道这里还没有意图。然后你自己来定型——AI 只做记录。

定型之后，才是实现。
