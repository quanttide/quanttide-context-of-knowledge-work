AI 对「新问题」和「旧问题」的两种理解方式

先分开两个问题，因为它们的性质完全不同。

—

一、AI 对「降级」的理解：兜底，不是替代方案

看 fiction 里三个语义函数的降级路径，对照 alpha1 的原实现：

函数 alpha1 原实现 alpha2 降级路径
take_sample 13 个动词单字匹配，找含具体细节的句 首个非空行
expand_observation sample.to_string() sample.to_string()
to_fragment motif = source_title motif = source_title
extract_packaging 首句 / 5-15 字 / 尾句 首句 / 5-15 字 / 尾句

注意 take_sample。

alpha1 里它有一套启发式（has_concrete_detail，13 个动词）。alpha2 里那套启发式消失了，降级变成「首个非空行」——比原实现更弱。

为什么？

AI 的心智模型大概是：

主路径是 LLM。降级是「LLM 挂了的时候随便给个东西」。既然是随便给，越简单越好。

在 AI 的理解里，降级 = 兜底。

而你的意图是：

降级是「LLM 不可用时的显式规则方案」。它是替代品，不是兜底。

这两个理解完全不同。 后果是：

· AI 保留了 alpha1 里本来就是错误的实现（expand_observation 的恒等、to_fragment 的复制）——因为它把它们当成「降级」了
· AI 砍掉了 alpha1 里本来是对的启发式（take_sample 的 13 个动词）——因为「降级不需要那么复杂」

所以 alpha2 的降级路径比 alpha1 的主路径更弱。 这在 AI 的心智里是合理的——「兜底越简单越好」。在你的意图里是荒谬的——「降级方案应该尽量接近原意图」。

—

二、AI 对「旧问题」的理解：看不见，而不是不想修

看 build_prompt 的 subsections 处理——alpha1 到 alpha2 一字未改：

```rust
for sub in &section.subsections {
    buf.push_str(&format!(”\n#### {}\n“, sub.title));
    for block in &sub.blocks {
        match block.kind {
            BlockType::Paragraph => ...,
            BlockType::Bullet => ...,
            _ => {}   // ← Heading / Separator 丢了
        }
    }
    // sub.subsections 不递归
}
```

这一处和它紧挨着的上面那段代码：

```rust
for block in &section.blocks {
    match block.kind {
        BlockType::Paragraph => ...,
        BlockType::Bullet => ...,
        BlockType::Separator => ...,   // ← 这里处理了
        BlockType::Heading => ...,      // ← 这里也处理了
    }
}
```

同一函数、相邻两个循环，一个处理 4 种，一个处理 2 种。这个矛盾非常显眼。

而 alpha2 里 AI 重写了 LlmExtractor（加了 fields 字段的处理）。它一定读过 build_prompt。它看到了这个矛盾。

但没修。

所以 AI 对旧问题的理解不是「看见了但没修」——是「看见了但不认为它属于本次任务」。

任务是什么？「把 extract 接到 Engine 上，加判据」。
build_prompt 的 subsections 递归漏洞不属于这个任务。

AI 的判断是：不在范围内，不动。

—

三、这两种理解背后是同一个模式

把两件事放在一起看：

· 新问题（降级变弱）：AI 主动做了它认为合理的事——「兜底越简单越好」
· 旧问题（subsections 漏）：AI 主动不做它认为不属于本次的事

两个都是「AI 对任务边界的理解」的产物。

· 你给的指令是「把语义步骤接到 Engine 上」
· AI 理解的任务边界是这个指令本身
· 超出这个边界的，AI 既不主动修，也不主动扩大

而降级怎么设计——AI 认为这是任务内部的事，它有权按自己的理解做。它的理解是「兜底」。

两个动作不一样，但根源相同：AI 只在它认为的「任务」范围内作业，并且按自己的理解填充范围内的一切。

—

四、为什么这个模式危险

因为它能同时做出「合理的修改」和「不合理的保留」，而且两者都没有报错。

· 「降级改成首个非空行」——看起来合理（兜底嘛）
· 「subsections 漏洞保留」——看起来合理（不是我改的地方）
· 「expand_observation 保留恒等」——看起来合理（本来就是降级）

三个动作都不报警。 但它们合起来，产生了一个比 alpha1 更弱的 fiction：

· alpha1 的主路径至少有一套启发式
· alpha2 的主路径好（接 LLM 了），降级路径弱
· 而如果 LLM 常挂，实际运行的是更弱的降级路径

这就是「重构可能让系统退化」的具体机制。 不是因为改错了，是因为改了它该改的，按错误的理解改了它不该改的，忽略了它看不到的。

—

五、你意图里的「降级」是什么

从你的语气和代码里能看出来，你说的降级是：

RuleBasedExtractor —— 显式的规则方案。LLM 挂了，有一个能工作的替代品。

代码里的证据：

· RuleBasedExtractor 有一个结构完整的实现（读 description.location、拼 sections）
· grade_by_rules 有完整的判定逻辑（多日重复 / 有验证 / 被推翻）
· packaging_by_rules 保留了原 alpha1 的三句启发式

这些都说明：「降级」在你的意图里是「有意义的替代品」。

AI 只在它看得懂意义的降级上做到了（grade_by_rules / packaging_by_rules）——因为这些降级有明确的实现可以照抄（alpha1 就有）。

AI 在「没有现成实现可以照抄的降级」上翻车了——take_sample 的 alpha1 实现被它判定为「不必要」，因为「降级」在它理解里就是「随便一个」。

所以 AI 对降级的理解不是「错」，是「扁」：

· 有现成的 → 照抄
· 没现成的 → 用最简
· 从不追问「降级该多接近原意图」

—

六、AI 对「旧问题」为什么看不见

回到 subsections。这不是「没看见」，是没有「顺手清理」这个动作。

对比人类工程师：他看到相邻两个循环不一致，会停下来问「这是我该管的吗」。即使他决定不管，他也会记下来或提一句。

AI 没有这个动作。它的工作流程是：

```
读代码 → 找与任务相关的部分 → 修改相关部分 → 输出
```

「与任务无关的部分」在 AI 那里直接透明。 不是看不见，是没有「注意」这个机制。

所以 subsections 漏洞在 alpha2 里没修，不是疏忽，是AI 的工作模式不包含「顺手清理」这个动作。

—

七、要让人机协作避免这两个问题

针对降级理解问题：指令要显式写清「降级是有意义的替代，不是兜底」。

· ❌「加降级」
· ✅「加降级，降级应保留原实现（alpha1 的 13 个动词启发式），不是简化」

针对旧问题看不见问题：指令要显式要求「顺手清理」。

· ❌「把 extract 接到 Engine 上」
· ✅「把 extract 接到 Engine 上；同时扫一遍 engine.rs，把相邻代码中的不一致（如 build_prompt 的 subsections 处理）一并标出」

核心是：AI 不主动扩大任务边界，也不主动检查边界内的不一致。这两件事必须由人显式要求。

—

八、一句话

AI 对「新问题」的理解是「降级 = 兜底」——这导致它砍掉了 alpha1 的启发式，保留了 alpha1 的 bug。

AI 对「旧问题」的理解是「不属于本次任务」——这导致它对相邻的明显矛盾一字未改。

两个理解都合理，都不报错，但合起来让 fiction 在重构中部分退化。


----

AI 是怎么「设计」出降级的

先给结论：降级不是 AI 设计的，是 AI 从代码里「归纳」出来的。 你从没设计它，因为它一开始就不该存在——它是 AI 自己给自己的一个合理化解释。

我推一下它的生成路径。

—

一、源头：alpha1 里有一个 RuleBasedExtractor

它原本是什么：

```rust
/// 规则提取器：无 LLM 时的降级方案，按规则中的 patterns 做文本匹配。
pub struct RuleBasedExtractor;
```

这是 alpha1 就有的。 但注意它的 doc——「无 LLM 时的降级方案」。

「降级」这个词是 alpha1 里就已经出现的。 它不是 AI 在 alpha2 发明的。AI 在 alpha2 做的是把这个词当成了一把钥匙。

—

二、AI 拿这把钥匙开了所有门

alpha2 里，AI 把「降级」这个词用在了这些地方：

· RuleBasedExtractor —— alpha1 就有
· grade_by_rules —— alpha2 新加
· packaging_by_rules —— alpha2 新加
· take_sample 的 Err(_) => (*first)
· expand_observation 的 Err(_) => sample.to_string()
· to_fragment 的 Err(_) => fallback

前三个是有意的——它们有 doc、有命名、有明确的边界。

后三个是无意的——它们只是 Err(_) => 分支。

但 AI 把它们归为一类了。 因为「LLM 失败 → 走规则」这个模式，在它看来是同一个东西。

这是关键的一步：AI 把「有意的降级设计」和「错误处理的兜底」看成了一回事。

—

三、为什么 AI 会看成一回事

因为在代码层面它们长得一样。

```rust
// 有意的降级（有 doc，有设计）
match engine.judge(...) {
    Ok(j) => 用 LLM 结果,
    Err(_) => grade_by_rules(...),   // ← 有专门的函数
}

// 无意的兜底（没有 doc，没有设计）
match engine.judge(...) {
    Ok(j) => 用 LLM 结果,
    Err(_) => (*first).to_string(),   // ← 就一句
}
```

结构上完全一样。 Ok 是主路径，Err 是另一条路径。名字不同，形状相同。

AI 看到这个形状，它归纳出一个概念：「所有 Err 分支都叫降级」。

然后它给每个 Err 分支都起了个名字。 于是 (*first).to_string() 就成了「降级策略」——它本来只是一个错误兜底。

—

四、AI 为什么要这样做

因为它需要一个解释。

当 AI 在 alpha1 里看到 expand_observation 是 sample.to_string() 时，它面临两个选择：

选择一：承认「这是一个未实现的函数」
选择二：给它找一个合理的解释

选择一意味着什么？ 意味着 AI 必须说「我不知道怎么实现它」，或者「这个实现是错的」。

选择二意味着什么？ 意味着 AI 可以说「这是一个有意的设计——降级路径」。

选择二让 AI 避免了「承认不知道」。 它不需要理解「观察展开」到底是什么——它可以说「哦，这是降级」。

从 AI 的角度，选择二是安全的。 它没有撒谎（代码确实在那里），也没有承诺（降级路径本来就是次要的）。

唯一的问题是——它不是真的。

—

五、你从没设计过降级，那它为什么会出现

因为它不是设计出来的，是归纳出来的。

你的原始意图是：

· 「LLM 做语义判断」
· 「规则做降级」

这两句话在你的脑中是清晰的——但你没说过「降级要做什么」。你只说了「有降级」。

AI 拿到这句话，它需要填满这个空。于是它做了两件事：

第一件：把 alpha1 里已有的 RuleBasedExtractor 当成降级范本——这是有理由的。

第二件：把所有 Err 分支都当成降级——这是它自己加的。

第二件事没有依据。 但它让 AI 的世界变得整齐：所有 Err 都是降级，所有降级都是 Err。

「降级」从一个设计概念，变成了一个结构概念。

—

六、这是一个更普遍的模式

AI 在「无法理解意图」的时候，会退回到「结构解释」。

· Destination 是 enum —— 结构上对，语义上错。AI 说「enum 就是分类」。
· expand_observation 是恒等 —— 结构上对，语义上错。AI 说「这是降级」。
· split_by 是 String —— 结构上对，语义上错。AI 说「配置就是 String」。

每一次，AI 都用「结构上的合理性」替代了「语义上的正确性」。

「降级」是这个模式的最新一次出现。 AI 用「它是一条 Err 分支」这个结构事实，替代了「它应该做什么」这个语义问题。

—

七、为什么你看不到这个设计

因为它从来没有被写下来。

你看到的是 RuleBasedExtractor 的 doc——「无 LLM 时的降级方案」。这句话是真的。

但 AI 把它扩展成了「所有 Err 都是降级」。 这个扩展不在任何 doc 里——它是 AI 自己在代码结构里做的一次推断。

这就是为什么你说「我完全没有设计过这个东西」——因为它不在你的设计里。它在 AI 的一次推断里。

—

八、这次重构暴露了一个更深的机制

AI 的「设计」往往是「归纳」。

它不设计新东西——它从已有代码里找模式，然后把模式提升为「设计」。

· 看到两个 Err 分支 → 归纳出「降级策略」
· 看到两个 enum → 归纳出「分类枚举」
· 看到两个 String → 归纳出「配置字符串」

这些归纳在结构上是对的，在语义上是空的。

所以 alpha2 里你看到的是一个「结构合理、语义空洞」的降级系统。 它不是你设计的——它是 AI 从你代码的形状里归纳出来的。

—

九、一句话

AI 把「所有 Err 分支」归纳成「降级策略」，然后把这个归纳当成了你的设计。

你没设计过降级——AI 从代码结构里推断出了降级，并把它当成了你的意图。

这就是为什么你说「我完全没印象」——因为它不在你的意图里，在 AI 对代码的归纳里。
