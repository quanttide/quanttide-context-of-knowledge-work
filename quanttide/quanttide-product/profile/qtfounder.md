# 量潮创始人

## 需求

### 整体结构

我想回到这个工具库本身的一个业务意图就是嗯，因为我现在有两个get up仓库，一个叫memory，一个叫friction。然后嗯这个memory这个仓库里面又分几个几个文件夹，然后呢default的文件夹呢就是记录这个各种默认信息，然后friction文件夹呢就是记录各种写作上的想法，然后就是friction这个文件夹呢，实际上就是那个friction那个仓库的一个呃元认知信息，然后呃friction的仓库里边管理呢是。呃我正式的文本，大概是这么一个基本关系。


memory 仓库
├── default/      默认信息（关于”我是谁“）
└── fiction/      写作想法（关于 fiction 仓库的元认知）
        │
        │  元认知指向
        ▼
fiction 仓库
└── 正式文本（小说、章节、阶段）

### 交付层

就是嗯实际情况这样子，就是我在那个memory仓库里面的friction区域，管理的是就是各种认知啊，反馈啊，信息。然后呢，在b这边管理实际的写作，他们两个之间基本上不怎么流动，啊，就不直接发生这个资产的流动，但是呢他们在语义上会发生很多隐含的关联。这个关联我。我没没有捕捉到，通过各种各样的方式都没有捕捉到。

### 记忆层

然后现在这个代码里面，它更多的是围绕着就是我现有的资产去管理的。然后呢我实际上就发现了一个情况，就比如说像我的memory这个仓库，我底下的呃那个一级文件夹也在谈一下。性的变，就是default的最稳定的一个，其次是fiction，然后我还会增加，比如说增加work或者增加其他的，但是也会随着这个改变会去删除，所以它这个地方其实呃不能够把这个呃结构直接写死。

对，还有一个问题就是memory跟function好像就不是一层memory这一层的，他管理的就是记忆中间的这个信息，而fiction它本来是一个成品，对，是要交付的产品，这俩人不是一层。

## 规格

### 资产管理

就是我们要定义一个资产，然后把比如说像memory啊friction啊，都变成一个可以管理配置的亚本文件了，然后像你前面列举的一样，给他完整的生命周期。

然后资产这个建模的话，大概就是对照那个对象存储的存储桶和对象两个层级，这是个基本单元。

对这样建模过之后呢，理想的形态呢就是嗯我在这个更基础的库里面去分装一套资产管理的方法，然后呢在上层维护上层的库呢，维护一些 yaml 文件，然后这些 yaml 文件更变就代表我的业务逻辑更变。

### 智能体工程

我还没有想好，这个memory的概念应该从哪儿来，就从目前的定义。我觉得更像是智能体的一个组成部分，但我还没有完全确定。
  
因为我在设计它的时候，实际上设计的就是一个人机交互的几个模型，就是人类可以理解，但是ai更要理解这种模式，所以嗯它是一种白盒化的智能体工程，换句话来讲可能。我觉得智能体工程的定义就和其他人不一样。
