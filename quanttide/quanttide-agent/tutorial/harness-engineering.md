你说得对，之前是工程要点。更本质地看，ICL 的弱点只有一句话：

ICL 是在前向传播中做“临时条件化”，而不是在参数中做“持久内化”，也不是在系统中做“确定性控制”。

所以 Agent 开发者的根本策略不是“优化提示词”，而是：把上下文承担不了的角色，全部外置给确定性系统。

—

一、本质矛盾：上下文被逼扮演三个它演不了的角色

Agent 设计里，上下文经常同时被要求当：

1. 规则手册：记住复杂约束、格式、流程；
2. 记忆库：记住历史、状态、用户偏好；
3. 执行器：精确调用工具、计算、按步骤执行。

但上下文只是有限的工作内存。它不是硬盘，不是编译器，也不是执行器。于是必然出现：

· 规则被注意力稀释，格式漂移；
· 记忆被窗口截断，长文退化；
· 执行靠概率生成，无法符号化保证正确；
· 错误无法通过信用分配稳定内化，下次还犯。

这就是 ICL 短板的根源。

—

二、逻辑推演：只有一条路——角色分离

既然上下文不能内化、不能持久、不能符号执行，那么：

不要让 LLM 做它不能可靠做的事。

把任务拆成两类：

· 开放语义任务：理解、归纳、规划、生成候选、模糊匹配 → 交给 LLM；
· 封闭正确性任务：规则、状态、格式、计算、流程、验证 → 交给外部系统。

所以 Agent 的本质不是“一个更聪明的模型”，而是：

概率性内核 + 确定性骨架 + 闭环验证。

—

三、四条设计公理

1. 上下文是工作台，不是内存。
   历史、状态、知识必须外部化。
2. 提示是接口，不是程序。
   规则应编译为 schema、代码、验证器、约束解码，而不是塞进 prompt。
3. 模型是提案器，不是执行器。
   LLM 输出的是候选，不是最终事实。必须经过验证。
4. Agent 是闭环系统，不是单体模型。
   可靠性来自编排、验证、回退，而不是来自单次推理。

—

四、落地：确定性骨架包裹概率内核

具体做法不是零散技巧，而是按上述逻辑映射：

· 规则外置：schema、代码、验证器、约束解码；固定高价值任务直接微调/蒸馏，把 ICL 变内化。
· 记忆外置：分层记忆、RAG、摘要+索引、外部数据库。
· 状态外置：状态机、工作流引擎、检查点，支持断点恢复。
· 执行外置：工具、代码执行、API、确定性编排，LLM 只决定“做什么”，不直接“做”。
· 正确性外置：提议—验证—修正循环，隔离上下文，限制迭代，动态路由模型。

参考流程：

用户请求 → 编排器（状态机） → LLM 规划/生成候选 → 检索外部记忆 → 工具/代码执行 → 验证器 → 通过则输出，否则回退/修正。

LLM 只出现在少数需要开放语义的节点。

—

五、一句话总结

Agent 可靠性 = 确定性骨架 × 概率内核 × 闭环验证。

LLM 负责开放语义，系统负责封闭正确。
扬长避短的本质，不是让模型变可靠，而是让系统在模型不可靠时仍然可靠。
